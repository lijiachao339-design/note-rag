# 设计文档：note-rag

> 这份文档由 **Claude Code plan mode（S 级模型）+ 你**共同产出。它的价值在于记录**取舍**，
> 而不是罗列功能。面试官会挑其中一条问"为什么"，你要能答上来。
>
> 填写建议：每个"决策"下面写 2-4 行，包含 ①当时的选项 ②为什么选它 ③它的代价。

## 1. 目标与非目标

**目标**（可验收）
- 检索我自己的 N 篇笔记，能回答"我上次在哪篇笔记里写过 X"
- 有客观指标：在 M 条标注问题上报告 recall@k / MRR / p95 延迟
- 以 MCP 工具形式接入 Claude Code 与 DSH，日常真实可用

**非目标**（明确不做，防止范围蔓延）
- 不做多用户 / 权限体系
- 不做 Web UI（命令行 + MCP 足够）
- 不做微调 / 训练（本机无 N 卡）

## 2. 关键决策

### 决策 1：切块策略

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 固定窗口 N 字符 | 实现最简单 | 会切断句子与语义单元；中文尤其碎 |
| 标题层级 + 段落边界 | 保留语义单元，breadcrumb 可作元数据 | 小节长度方差大，需要合并策略 |
| 语义切块（按 embedding 相似度） | 边界最自然 | 慢、贵，且需要额外评测才能证明有效 |

**结论**：采用标题层级 + 段落边界；超长小节按段落切并保留字符重叠。
**代价**：需要一条"小节是否合并"的规则，这条规则本身需要消融实验验证。
**度量**：同一评测集下与固定窗口方案对比 recall@5。

### 决策 2：融合方式

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| 分数加权求和 | 可调权重，表达力强 | 两路分数量纲不同，换语料就要重新标定 |
| RRF（只用排名） | 无需标定、鲁棒、一行数学 | 丢弃了分数幅度信息 |
| 学习排序（LTR） | 上限最高 | 需要标注数据与训练流程，投入产出比不划算 |

**结论**：RRF（k=60）。
**代价**：放弃了"向量相似度极高时压过 BM25"的能力。
**度量**：与加权求和、与 round-robin interleave 做三方对比。

### 决策 3：存储

**结论**：Postgres + pgvector（HNSW），关键词检索在进程内 BM25。
**为什么不用专用向量库**：1 万 chunk 规模下没有性能必要，且会多一个运维组件；
Postgres 复用事务与备份。**为什么不用 pg FTS 做关键词检索**：`simple` 词典不切分中文。

### 决策 4：评测粒度

**结论**：note 粒度（"这条笔记能否回答问题"），不是 chunk 粒度。
**为什么**：chunk 级人工标注不可扩展，而人真正能判断的是"笔记里有没有答案"。
**代价**：无法区分"同一篇笔记里检索错了段落"这类细粒度错误。

## 3. 评测协议

- 数据集：`eval/dataset.jsonl`，≥200 条，含 5%~10% **不可回答**的问题（用于暴露幻觉式检索）
- 生成方式：廉价模型批量生成候选 → 强模型抽检 → 人工确认答案确实存在于该笔记
- 指标：recall@{1,5,10}、MRR、nDCG@10、p50/p95 延迟
- 消融维度：切块方案 / 融合方式 / 是否 rerank / embedding 模型
- 记录方式：每次实验在 `docs/adr/` 或 Obsidian 里留一条记录，标明 commit 与指标

## 4. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 自建评测集有偏（问题由模型生成，措辞接近笔记原文） | 指标虚高，实际不好用 | 加入手写的、口语化的问题；加入不可回答的问题 |
| 离线 hashing 嵌入没有语义能力 | 同义改写查不到 | 明确区分"链路正确性"与"语义质量"两组实验；后者接真实嵌入模型 |
| 中文分词是近似方案 | 关键词召回有损 | 与 `pg_bigm`/`zhparser` 做对比实验 |
| 笔记含隐私内容 | 泄漏风险 | 检索服务只监听本机；MCP 走 stdio；不部署到公网 |
