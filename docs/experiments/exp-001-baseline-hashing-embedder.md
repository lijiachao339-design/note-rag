# 实验 EXP-001：离线 hashing 嵌入的基线检索质量

- **日期**：2026-09-18
- **相关 commit**：`2db386a`（跑评测时的 HEAD）
- **数据集**：`eval/dataset.jsonl`，198 行 = 180 条可回答问题（135 EN + 45 ZH）+ 18 条不可回答问题
- **语料**：1947 篇 markdown / 13.41 MB，索引为 17520 个 chunk
- **语料指纹**：`9854a816415b1a9579b6786af6f975f19af4e06f`

## 假设

在换成真实语义嵌入模型之前，先用**离线 hashing 嵌入**（feature hashing，无需 API key）建立基线。
预期：它能跑通全链路，但语义能力为零，因此 `vector` 模式应显著弱于 `keyword`（BM25）。

## 方法

```powershell
uv run note-rag eval --dataset eval/dataset.jsonl --out eval/out/ablation.md
```

四种模式共用同一份实现（`src/note_rag/retriever.py`），区别只在取哪一路召回：

| 模式 | 召回方式 |
| --- | --- |
| `vector` | 仅 pgvector 余弦相似度 |
| `keyword` | 仅进程内 BM25 |
| `hybrid` | 两路 RRF 融合（k=60，等权） |
| `hybrid_rerank` | hybrid + reranker（**当前是 no-op，故意不假装有提升**） |

评测在 **note 粒度**上打分：结果先去重到"每篇笔记取最佳 chunk"，再用 `relevant_notes` 算
recall@k / precision@k / nDCG@k / MRR 与 p50/p95 延迟。不可回答问题的 `relevant_notes` 为空数组，
按"记 0 分但保留在均值里"计入（见 `metrics.py` 的口径说明）。

## 结果

| metric | vector | keyword | hybrid | hybrid_rerank |
| --- | --- | --- | --- | --- |
| recall@1 | 0.1768 | **0.5758** | 0.2778 | 0.2778 |
| recall@5 | 0.2677 | **0.7879** | 0.6111 | 0.6111 |
| recall@10 | 0.3182 | **0.8283** | 0.7525 | 0.7525 |
| precision@10 | 0.0320 | **0.0828** | 0.0753 | 0.0753 |
| nDCG@10 | 0.2445 | **0.7049** | 0.4857 | 0.4857 |
| MRR | 0.2216 | **0.6650** | 0.4031 | 0.4031 |
| p50 (ms) | 33.4 | 528.1 | 528.1 | 547.9 |
| p95 (ms) | **54.0** | 709.2 | 733.5 | 774.2 |

## 结论

假设成立，而且比预期更极端：**`hybrid` 明显差于 `keyword`**。

### 1. hashing 嵌入不是语义检索，而是"有损的词法检索"

它按 token 哈希到固定维度（384）的桶里。同一个 token 在查询与文档里会落到**同一个桶**，
所以它确实带了词法信号——但代价是哈希冲突把不同 token 混进同一个桶，形成噪声。

证据：随机排序在 1947 篇里的 recall@10 约为 `10 / 1947 ≈ 0.5%`，而 `vector` 拿到 **31.8%**——
远好于随机，说明它抓住了词法重合；但与 BM25 的 **82.8%** 相比差距巨大。

**所以 `vector` 这一列衡量的不是"语义检索能力"，而是"退化后的词法检索能力"。**
把它当成语义基线会得出错误结论。

### 2. RRF 无法拯救一路无效的召回器，它只会把噪声平均进来

`hybrid`（0.6111 @5）落在 `vector`（0.2677）与 `keyword`（0.7879）之间，正好符合"融合一个强召回器
与一个弱召回器"的预期。这是 RRF 的正确行为——**RRF 保证的是鲁棒性，不是免费的性能提升**。
要让它产生增益，前提是两路召回各自都有效且**互补**。

### 3. `hybrid_rerank` 与 `hybrid` 完全一致，这是刻意的诚实

`Reranker` 默认实现是原样返回（no-op），所以两列数字必然相同。这样做的目的是：
**表格必须如实反映"还没实现"，而不是造出一个假的提升。** 真要出提升，得先接入 cross-encoder。

### 4. 延迟瓶颈在 BM25，不在向量检索

`keyword` 的 p95 是 **709 ms**，而 `vector` 只有 **54 ms**——差了 13 倍，与直觉相反。
原因是 `bm25.py` 目前对查询词做**全量扫描**：每次查询都要为 17520 个文档算一遍分数。
这是纯 Python 全表的代价，且与语料规模线性相关。

## 下一步（按预期收益排序）

| 优先级 | 动作 | 预期 | 度量方式 |
| --- | --- | --- | --- |
| **P0** | 换真实嵌入模型（OpenAI 兼容 `/v1/embeddings`），`ingest --full` 重建 | `vector` 大幅上升，`hybrid` 超过 `keyword` | 重跑本实验，对比同一数据集 |
| **P0** | 给 BM25 建倒排索引（term → postings + 只对候选打分） | p95 从 709 ms 降到 50 ms 量级 | 同上表的 p95 行 |
| P1 | 接入 cross-encoder reranker（`bge-reranker-base`，CPU） | `hybrid_rerank` 的 recall@5 提升，同时报出延迟涨幅 | 新增一列对比 |
| P2 | 负样本占比提高到 15%~20% | 检验"永远返回 Top-10"是否被惩罚 | 观察各模式在负样本上的表现 |

> 关于 P0 的嵌入模型：本机无 NVIDIA GPU，走 API 是唯一现实选择。切换后**必须 `--full` 重建索引**，
> 因为 `vector(dim)` 在建表时就固定了；换模型同时换维度会让插入直接报错（见 `AGENTS.md` 遗留项 6）。

## 这次实验暴露的方法论问题（值得记住）

1. **问题语言必须与正文语言一致**：第一版数据集用中文问英文笔记，在纯词法检索下重合度为 0，
   四种模式都会接近全 0——那测的是"没有语义嵌入"，而不是检索设计。已重跑并校验 180/180 一致。
2. **`answer_span` 必须能在原文里逐字找到**：编译器脚本用这一条做零成本的幻觉闸门，
   第一版 180 条里有 5 条被这条规则拦下。比再叫一个模型来判断更可靠、更便宜、还可复现。
