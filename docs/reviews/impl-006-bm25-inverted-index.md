## 1. 先修正前提：瓶颈的 83% 是重复分词，不是"扫描"

`bm25.py` 旧版 `search()` 对**每个文档**调用一次 `score()`，而 `score()` 内部写着
`for term in tokenize(query)` —— 于是一次查询把 query 分词了 **17,524 次**。
`idf(term)` 同理，每个 (文档, 词) 组合重算一次 `math.log`。

| 成分 | 耗时 | 占比 |
| --- | --- | --- |
| `tokenize(query)` × 17,524 | ~454 ms | **~83%** |
| 遍历 17,524 个文档的空循环 | 0.5 ms | 0.1% |
| 其余（dict 查找、打分、排序） | ~90 ms | ~17% |

**单独验证**：只把 `tokenize`/`idf` 提到循环外、数据结构一字不改，
**462 ms → 119 ms（省 74%），30 条查询逐位相同**。

倒排索引省的是另一件事：query term 的 postings **并集是 100% 的文档**
（语料里 `agent` 的 df = 17,524，出现在每一篇），所以它**并不缩小候选集**；
它省掉的是 **tf=0 的无效组合**——从 17,524 × 34 ≈ 596,000 次 dict 查找，
降到只遍历 **42,914** 个真实 posting（≈14× 内层操作）。

> 如果只报"建了倒排、快了 38×"，读者会以为加速全部来自数据结构。实际是
> **74% 来自把分词提出循环，剩下的来自倒排 + top-k 选择**。

## 2. 实际改了什么

全部集中在 `src/note_rag/bm25.py`（`retriever.py`、`api.py`、`cli.py` 一行未动——
`BM25` 的公开契约 `add/extend/remove/score/search/top_terms/idf/__len__` 保持不变）。

| 位置 | 改动 |
| --- | --- |
| `bm25.py:75-78` | `_rank_key()`：抽出排序键 `(-score, doc_id)`，`search` 的两条分支共用，确定性 tie-break 只有一处定义 |
| `bm25.py:104-127` | 新布局：`_slots` / `_index_of` / `_free` / `_doc_terms` / `_doc_len` / `_total_len` / `_live` / `_postings` / `_posting_tfs` / `_norms` |
| `bm25.py:129` | `_avgdl` 变成 `@property`，由 running sum 得出 → **O(1)**（旧版每次 `add()` 都 `sum(_doc_len.values())`，整体 O(n²)） |
| `bm25.py:131-168` | `add()`：分配 slot（优先复用 `_free`），写 postings；常见情况 `append`，复用 slot 时 `bisect.insort` 以保持升序 |
| `bm25.py:170-195` | `remove()`：**立即清理** postings（`bisect_left` 定位后 `del` 两个平行列表），不用墓碑 |
| `bm25.py:197-205` | `_ensure_norms()`：长度归一化项的惰性缓存，任何写操作置 `None` |
| `bm25.py:207-214` | `document_frequency()`：df = posting 列表长度（见 §3.3） |
| `bm25.py:222-240` | `score()`：改为按 `bisect` 在 postings 里取 tf，**保持 `for term in tokenize(query)` 的遍历顺序** |
| `bm25.py:242-275` | `search()`：分词/idf 提到循环外；按 postings 累加进稠密 `scores` 数组；`heapq.nsmallest` 取 top-k |
| `bm25.py:14-19`（模块 docstring） | 记录"查询里重复的词会被计两次分"这个既有怪癖（见 §3.2） |
| `tests/test_bm25_equivalence.py` | **新增**：把旧实现内联为参考实现，做逐位对比 |

`tests/test_bm25.py` 的 11 条行为契约**一个字没改**，全部通过。

### 3.2 为什么能做到逐位相同（不是"差异可忽略"）

设计 §2.3 论证过，实现严格照做：

- **累加顺序不变**。旧版对文档 d 的累加是「按 `tokenize(query)` 顺序、跳过 tf=0」。
  新版外层遍历 `tokenize(query)`、内层遍历该 term 的 postings —— 对任意固定的 d，
  贡献到达的先后完全一致（"d 不在 postings[t] 里" ⟺ 旧版的 `tf == 0` 被 `continue`）。
- **表达式逐字保留**：`idf * (tf * (k1 + 1)) / (tf + norm)`，结合顺序不变。
- **`avgdl`**：`sum(dict.values())/n` 换成 `_total_len/n`，分子都是整数精确和，一次浮点除法。
- **`heapq.nsmallest(n, it, key)`** 在 CPython 文档里被定义为等价于 `sorted(it, key=key)[:n]`；
  key 是 `(-score, doc_id)` 而 doc_id 唯一 ⇒ **全序、无并列**，稳定性差异无从体现。

> **保留的既有怪癖**：`tokenize()` 返回**带重复**的列表，`score()` 直接遍历它，
> 所以**查询里出现两次的词会被计两次分**。这不是标准 BM25。
> 本轮的硬要求是逐位等价，所以**原样保留**，并写进了模块 docstring。
> 要改成标准做法，会改变 `docs/experiments/` 里的每一个历史数字，**必须单独立项**。
> 等价性测试里专门有 40% 的查询带重复词，确保这个行为不会被后续重构悄悄改掉。

### 3.3 实现时相对设计的一处偏离：删掉了 `_df`

设计里写的是"df 仍然用 `Counter` 维护"。实现时发现那是**同一事实的第二份副本**：
一个 term 的 df 就是它 posting 列表的长度。单独再存一个 177,604 项的 `Counter`
既多花 **0.39 s** 构建时间，又给"两份数据不同步"留了口子。

改成 `document_frequency(term) -> len(self._postings.get(term, ()))`（`bm25.py:207-214`），
`idf()` 在其之上。**值完全相同**（df 的定义就是含该 term 的文档数），
所以不影响等价性；`remove()` 也因此少了一段手工维护 df 的代码。
已回填到 `design-006` §1.1 作为"实现时的偏离"。

## 4. 延迟验收（沿用 Batch B 的方法：3 轮重复、模式在每轮交错执行）

### 4.1 对照表

| mode | 前 p50 | **后 p50** | 前极差 | 后极差 | 前 p95 | **后 p95** |
| --- | --- | --- | --- | --- | --- | --- |
| vector | 47.9 | 47.9 | 0.1 | 0.2 | 51.5 | 51.6 |
| **keyword** | 349.7 | **9.1** | 11.6 | **0.3** | 503.4 | **15.5** |
| hybrid | 396.5 | **58.6** | 4.1 | 0.5 | 550.5 | **66.7** |
| hybrid_rerank | 397.2 | **58.5** | 30.7 | 0.7 | 554.2 | **66.1** |

**验收线 `p50 < 320 ms`：`keyword` = 9.1 ms，达到，且低了一个数量级以上。**

### 4.2 顺带：测量本身变稳了

重复间极差从 11.6 / 30.7 ms 降到 **0.3 / 0.7 ms**。
impl-004 §5.4 抱怨过"每次运行都有一个随机落点的离群轮次，导致可区分性判断在两次运行里相反"
—— 那个现象在 `keyword`/`hybrid` 上基本消失了，因为这两路的耗时本身缩了一个数量级，
机器抖动的绝对值不再能盖过模式间差异。

### 4.3 可区分性（判据：中位数之差 ≤ 较大极差 → 不可区分）

| 比较 | p50 差 | 较大极差 | 结论 |
| --- | --- | --- | --- |
| keyword vs vector | 38.8 | 0.3 | 可区分 |
| keyword vs hybrid | 49.5 | 0.5 | 可区分 |
| vector vs hybrid | 10.7 | 0.5 | 可区分 |
| **hybrid vs hybrid_rerank** | **0.1** | 0.7 | **不可区分** |

`hybrid` 与 `hybrid_rerank` 差 0.1 ms 而噪声 0.7 ms —— 对一个 no-op reranker，这是正确答案
（Batch B 那次单轮测量曾显示两者差 30 ms，是纯噪声）。

### 4.4 瓶颈换人了

`keyword` 现在是**最快**的模式（9.1 ms），比 `vector`（47.9 ms）还快 5×。
而且 `hybrid`（58.6）≈ `vector`（47.9）+ `keyword`（9.1）+ 融合开销（≈1.6 ms）——
**加性结构第一次变得可见**，以前被 BM25 的 350 ms 完全淹没。

**剩余瓶颈明确落在向量这一路**：47.9 ms 全部是 pgvector 的一次网络往返 + HNSW 检索
（`ef_search=200`，本轮禁改）。想再快就得动那一边，与 BM25 无关。

分语言看，`keyword` 的查询耗时：**EN 8.3 ms / ZH 11.1 ms** —— 中文仍贵 34%，
因为一句中文问题产出约 50 个 token 而英文只有 17 个（impl-005 §2.5 测过），
倒排索引不改变这个事实，只是把绝对值缩小了。

## 5. 内存与启动成本（实测）

### 5.1 常驻内存

`tracemalloc` 实测同一份 17,524 chunk 语料：

| | 常驻 |
| --- | --- |
| 旧实现（每文档一个 `Counter`） | 246.5 MB |
| **新实现（倒排 + 每文档 term 元组）** | **272.4 MB** |
| 差 | **+25.9 MB（+10.5%）** |

设计里预估 "~280 MB"，实测 272.4 MB，估得基本准。
（设计 §1.2 的分层测量里，倒排本身 88.2 MB、每文档 term 元组 +23.4 MB、
被替换掉的 `Counter` 布局 78.7 MB —— 删掉 `_df` 又省回来一部分。）

### 5.2 构建时间与复杂度

| 文档数 | 旧实现 | 新实现 | 新/旧 |
| --- | --- | --- | --- |
| 4,381 | 0.73 s | 1.08 s | 1.48× |
| 8,762 | 1.71 s | 2.35 s | 1.38× |
| 17,524 | 3.86 s | 4.91 s | **1.27×** |

**比值在单调下降**，因为旧版 `add()` 每次都 `sum(_doc_len.values())` —— 那是 O(n²)，
实测在 17.5K 规模上就占了约 1.15 s；新版是 running sum，O(1)。
外推下去两条曲线大约在 **3–4 万 chunk 处交叉**，此后新实现构建更快。
也就是说：**+1.05 s 是当前规模下的一次性代价，且随语料增长会自动消失。**

### 5.3 API 启动成本：结论是"暂时不需要异步化"

`build_keyword_index()` 端到端实测 **4.67 s**，其中：

- 从 Postgres 读 17,524 行：**0.16 s**（3%）
- 建索引（分词 + 倒排）：**4.51 s**（97%），其中光分词就占 2.18 s

任务书问"lifespan 里同步建索引是否还合适"。**我的判断：暂时合适，不建议现在异步化。**

- 4.7 s 的冷启动对一个单机知识库服务可以接受，而异步化要引入"索引未就绪时怎么办"的
  状态机——`retriever.py` 的 `_ensure_index()` 现在保证了"漏建索引不会静默降级"
  （review-001 的那个 bug），异步化会把这条不变量重新变复杂。
- 真要降，**优先降的不是并发而是分词**：2.18 s / 4.51 s 是分词，而分词结果在
  `ingest` 时其实已经算过一次却没留下。把 token 或 postings 持久化到 Postgres，
  启动就变成纯 I/O。这比后台线程更值得做，但属于另一个题目。

## 7. 仍然没做的事 + 下一步

### 本轮明确不做（设计 §6 列过，这里复述结论）

| 不做 | 为什么 |
| --- | --- |
| 高 df term 剪枝 / 停用词 | 收益很大（`agent` 的 df=100%、idf≈2.9e-5，几乎不影响排序却要遍历 17,524 个 posting），**但会改变分数**，与"逐位等价"直接冲突。必须单独立项并重跑基线。 |
| WAND / MaxScore 动态剪枝 | 同上，且只有 top-k ≪ N 时才划算 |
| `array('i')` 紧凑 postings | 实测缓冲区省 16.9 MB，但容器开销另有 42 MB，查询还慢 6% |
| 修"查询重复词计两次分" | 会改变所有历史数字（§3.2） |
| `build_keyword_index()` 异步化 | 见 §5.3，先持久化分词结果更值得 |

### 建议的下一步（按性价比）

| 优先级 | 动作 | 预期 | 怎么验收 |
| --- | --- | --- | --- |
| **P0** | 换真实嵌入模型（一直挂在 exp-001 的下一步） | 检索质量，不是延迟 | impl-005 §4 的中英差值 CI 是个免费探针 |
| P1 | **向量这一路现在是瓶颈**（47.9 ms，占 `hybrid` 的 82%）：先测清楚是网络往返还是 HNSW 本身 | 若是往返，批量/连接池可降；若是 HNSW，与 `ef_search` 权衡 | 同一套 3 轮重复方法 |
| P1 | 把 `ingest` 阶段算好的 token/postings 持久化，启动变纯 I/O | 4.67 s → 亚秒级 | 实测 `build_keyword_index()` |
| P2 | 停用词 / 高 df 剪枝，作为**独立实验**（会改数字） | 查询再降数倍；可能**提升**排序质量（去掉 idf≈0 的噪声） | 新建 exp，前后对照四张表 |
| P2 | 标准化"查询重复词只计一次" | 与教科书 BM25 对齐 | 同上，单独立项 |

### 一条给未来的提醒

本轮最值得记住的不是"建了倒排"，而是**在动数据结构之前先量一次成分**：
83% 的时间花在一个可以用三行代码消除的重复计算上。
如果一上来就照着"全量扫描"这个假设去写倒排，拿到的仍然是同样的加速，
但**归因会是错的**，而错的归因会让下一次优化押错地方。
