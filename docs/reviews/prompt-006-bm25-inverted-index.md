## 目标

`src/note_rag/bm25.py` 目前对**每次查询都全量扫描全部文档**（17524 个 chunk）。
实测 `keyword` 模式 p50 中位数约 **338 ms**、p95 量级 **709 ms**，而 `vector` 只有 **48 ms** ——
瓶颈完全在这一路，且与语料规模线性相关。

**验收判据（由你在 Batch B 的延迟测量规范化中定下）**：改造后 `keyword` **p50 中位数 < 320 ms**。
这条线当时是照着"单次运行不可区分"的噪声水平画的，本轮要用同样的方法复测。

顺带目标：把启动成本（`build_keyword_index()` 读 17524 行并建索引）报出来，并判断
API 的 lifespan 里同步建索引是否还合适。

## 第二步：实现

**等价性是硬要求**：改造后在 **strict 视图**下，`keyword` 的 `recall@1/5/10`、`MRR`、`nDCG@k`
必须与改造前**逐位相同**。基线就在 `eval/out/ablation.json` 里（已提交进版本库），
`docs/experiments/exp-002-*.md` 也记了早期数字。

如果不等价：**不要调容差蒙过去**。要么修到等价，要么把差异的根因说清楚
（例如浮点累加顺序），并**完整记录一个新基线**（前后对照 + 为什么可接受）。

同时：

- 补等价性测试（随机查询对比新旧打分）。注意 `tests/` 里现有 `test_bm25.py` 的**行为契约**必须继续成立。
- `mypy --strict` 零错误、不引入新依赖、`ruff` 全绿。
- 保持确定性：同分时 tie-break 到 `doc_id`（现在就是 `(-score, doc_id)`）。

## 第三步：用同一套方法验收延迟

- 如果 `p50 < 320 ms` 没达到，**如实报**，并给出剩余瓶颈在哪（候选集打分？top-k 选择？分词？）。
