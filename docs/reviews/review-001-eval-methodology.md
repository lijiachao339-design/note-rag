## S1（最高）问题与目标笔记之间存在词法泄漏，整张消融表测的是"词法重合"而不是"检索能力"

**现象**：评测问题是由模型**读着某篇笔记**生成的，它们系统性地把该笔记里的稀有标识符逐字抄进了问题。
按"问题与目标笔记共享的最稀有 token 在全语料的文档频率（df）"分组，实测：

| 共享的最稀有 token 的 df | n | `keyword` R@5 | `vector` R@5 | `hybrid` R@5 |
| --- | --- | --- | --- | --- |
| ≤2（近乎唯一指纹） | 31 | **1.000** | 0.516 | 0.806 |
| 3–10 | 40 | 0.900 | 0.350 | 0.700 |
| 11–50 | 72 | 0.889 | 0.361 | 0.722 |
| >50（没有稀有词可抄） | 37 | **0.676** | 0.216 | 0.405 |

180 条可回答问题里，**50 条（27.8%）**与目标笔记共享一个 df ≤ 5 的 token。
问题里 df ≤ 50 的低频词中，平均 **41%**（中位数 33%）在目标笔记里逐字存在。
肉眼看样本也是这个味道：`dsh.client.external`、`dsh-home-paths`、`facadeModuleId`、`ThinkRow`、
`settings.describe` 都直接出现在问题文本里。

**为什么是问题**：df ≤ 2 那一组 BM25 拿满分——那不是检索，那是精确匹配一个几乎唯一的字符串。
整个 `keyword` 列的 0.8667（答题子集）里有一大块是这么来的。
于是"`keyword` ＞ `hybrid` ＞ `vector`"这个结论，很大程度上是**数据集构造方式**的产物：
一个专门奖励逐字重合的评测集，当然会让纯词法检索赢。
这也是为什么必须先修它——它决定了第 6 问的答案。

**位置**：`scripts/build_eval_dataset.py:170-186`（校验环节只管长度、元问题、span 存在性，
**没有任何一条约束"问题不得照抄笔记里的稀有标识符"**）；
`scripts/build_eval_dataset.py:39` 的 `META_PATTERNS` 只拦了"这篇笔记/标题是什么"这类，拦不住词法抄写。

**最小修复**（不需要重新生成问题）：在编译期加一条**泄漏闸门**，和现有的 `answer_span` 闸门放在一起：

1. 用 `note_rag.bm25.tokenize` 对全语料算一次 note 级 df（一次性，几秒）。
2. 对每条候选问题，取"问题 ∩ 目标笔记"的 token 里最小的 df；若 `min_df <= 2` 则丢弃或标记
   `leak: true`，并在 `eval/dataset.report.md` 里单独出一张分布表。
3. 报告时**分组出数**（就用上面那张表的分组），而不是只给一个总均值。

即使一条都不丢，只要把这张分组表放进 `docs/experiments/`，结论的可信度就完全不一样了：
读者能自己看到"去掉指纹词之后 BM25 掉到 0.676"。

## S2（高）3 条问题指向一篇**索引器根本不会索引**的笔记，所有模式永久记 0

**现象**：语料目录里有 1947 个 `.md`，但 `collect_chunks` 只扫到 **1945** 篇。缺的两篇是：

```
.agents__notes__archived__AGENTS__da377771.md
.agents__notes__implemented__AGENTS__b84ef955.md   ← q0001 / q0002 / q0003 的目标笔记
```

原因是两套文件发现规则不一致：

- `src/note_rag/notes.py:267` —— `if not include_hidden and any(part.startswith("."))` 跳过隐藏路径。
  语料是**扁平化命名**的，文件名本身就以 `.agents__` 开头，于是被当成隐藏文件跳过。
- `scripts/build_eval_dataset.py:149` —— `corpus_dir.glob("*.md")`。
  pathlib 的 glob **包含**点开头的文件（和 shell 的 `*.md` 不同），所以评测集收录了它。

**为什么是问题**：q0001–q0003 对任何检索器都不可能命中，是白扣的 3/180 = 1.67%。
它不是"检索没做好"，是"目标不在索引里"。而且 `docs/experiments/exp-001-baseline-hashing-embedder.md:6`
写的是"语料 1947 篇 markdown"，与实际索引的 1945 篇对不上——这个口径不一致会一直传下去。

**最小修复**（二选一，都是一行）：

- 编译期对齐：`build_eval_dataset.py` 改用 `note_rag.notes.iter_vault_files(corpus_dir)` 来枚举语料，
  让评测集与索引器共用同一个发现规则（同时顺手修掉 S10 的路径口径问题）。
- 或者在 `cmd_eval` 里加一个开场断言：`qrels` 里出现的所有 note 必须存在于
  `store.corpus_stats(conn)` 的 note 集合中，否则直接报错而不是静默记 0。

我推荐**两个都做**：前者治本，后者保证以后同类问题会当场炸而不是变成一个漂亮的低分。

## S3（高）`vector` 一列被 ANN 近似额外拉低了约 9 个点，exp-001 把这部分错误归因给了"嵌入没有语义"

**现象**：用**同一份** hashing 向量、同一份 chunk、**精确**余弦重跑 `vector`：

| | recall@1 | recall@5 | recall@10 | mrr |
| --- | --- | --- | --- | --- |
| 记录值（走 Postgres） | 0.1768 | 0.2677 | 0.3182 | 0.2216 |
| 精确余弦（离线复现） | 0.1919 | **0.3232** | **0.4091** | 0.2570 |

recall@10 差 **9.1 个点（相对 +28.6%）**。同一套离线复现把 `keyword` 一列逐位复现了，
所以差异被隔离在**向量这一路**。

**为什么是问题**：`docs/experiments/exp-001-baseline-hashing-embedder.md:50-59` 把
"`vector` 只有 31.8%"整个归因于"hashing 嵌入不是语义检索"。实测表明其中约四分之一
是**检索配置**造成的，不是嵌入能力造成的。归因错了，`下一步` 表里 P0 的预期收益也会估错。

**位置**：

- `src/note_rag/store.py:41-42` —— `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`，
  HNSW 是近似检索。
- `src/note_rag/retriever.py:131` / `src/note_rag/store.py:168-188` —— 请求 `limit=50`
  （`candidate_k` 默认 50，`config.py:38`），而 pgvector 的 `hnsw.ef_search` 默认是 **40**。
  ef_search 小于 limit 时召回会明显掉，这是第一嫌疑。
- 顺带一提：`vector(384)` 在 pgvector 里是 **float4**，与离线 float64 有量化差异，
  但那只影响并列项的次序，解释不了 9 个点。

**这一条请先验证再下结论**（我没有数据库连接，无法直接证实）。最小验证/修复：

```sql
SET hnsw.ef_search = 200;   -- 或 SET LOCAL，放在 eval 的连接里
```

在 `cmd_eval` 建立连接后执行一次，重跑 `vector` 一列。若数字向 0.4091 靠拢，就坐实了。
然后把 `ef_search` 写进 `Settings`（`config.py`）并**记进实验文档的方法一节**——
检索参数不记录，等于数字不可复现。

**附带影响**：`CLAUDE.md` 的约束表要求 "`fusion.py` 排序必须确定性（tie-break 到 id）"，
理由是"否则评测数字不可复现"。但向量这一路走 ANN，端到端的确定性其实**没有保证**：
重建一次索引，`vector` 与 `hybrid` 两列都可能漂移。这一点值得在约束表里补一句。

## S4（高）18 条不可回答问题在三个指标上**恒等于 0**，零判别力——它不是幻觉闸门，只是一个 0.909 的缩放因子

**任务书第 2 问的直接回答。**

**现象**：`relevant_notes` 为空数组时：

- `recall_at_k` —— `metrics.py:40-41`，`if not grades: return 0.0`
- `reciprocal_rank` —— `metrics.py:61-62`，同样返回 0.0
- `ndcg_at_k` —— `metrics.py:86-90`，`idcg == 0` → `return 0.0`

三者**与检索器返回了什么完全无关**。返回 10 篇垃圾、返回 1 篇垃圾、返回空列表，得分都是 0.0。

**为什么是问题**：

1. **它不惩罚"合理地返回空结果"，但也不奖励**——而"不奖励"在这里是更严重的毛病。
   一个正确拒答的检索器和一个硬凑 10 篇的检索器拿到**完全一样**的分数。
   所以这 18 行**没有提供任何信息**，只是把所有模式的所有指标统一乘了 `180/198 = 0.9091`。
   `metrics.py:8-10` 的模块注释说"这就是你抓住幻觉式检索器的办法"——**代码里不成立**，
   应当修正注释或修正实现。`tests/test_metrics.py` 里那条
   `test_recall_with_no_relevant_documents_is_zero_not_error` 的注释同样固化了这个误解。
2. `exp-001` 的 `下一步` 表 P2 写着"负样本占比提高到 15%~20%，检验'永远返回 Top-10'是否被惩罚"。
   在当前实现下，提高占比**只会把所有数字等比压得更低**，永远检验不出任何东西。
3. 顺带：`metrics.py:118` 之后 `evaluate` 的返回值被 `cmd_eval` 塞进了 `p50_ms`/`p95_ms`，
   而 `tests/test_metrics.py::test_metrics_are_bounded` 断言所有值在 [0,1]——
   这条断言只在 `evaluate` 的原始输出上成立，别再往里加无界字段了。

**换算给你**：现在的数字乘 `198/180 = 1.1` 就是"只算可回答问题"的数字：

| | recall@1 | recall@5 | recall@10 | mrr |
| --- | --- | --- | --- | --- |
| `keyword` 全集(198) | 0.5758 | 0.7879 | 0.8283 | 0.6650 |
| `keyword` 可回答(180) | **0.6333** | **0.8667** | **0.9111** | **0.7315** |
| `hybrid` 可回答(180) | 0.3778 | 0.6667 | 0.8444 | 0.5056 |
| `vector` 可回答(180)（精确余弦） | 0.2111 | 0.3556 | 0.4500 | 0.2827 |

**最小修复**（拆成两张表，不要混在一起）：

1. **排序质量表**只在 180 条可回答问题上算 `recall@k / MRR / nDCG@k`。
   `cmd_eval` 里按 `row["answerable"]` 切片，`evaluate` 一行都不用动。
2. **拒答表**单独报，需要一个置信信号。实测可行性（BM25 top-1 分数）：
   - 可回答：均值 53.6 / 中位数 47.1 / 最小 21.4
   - 不可回答：均值 39.2 / 中位数 37.3 / 最大 68.3
   - **AUC = 0.729**；最优单阈值 `t = 42.75` → 保住 61.7% 可回答，拒掉 88.9% 不可回答。

   有信号，但很弱——这本身就是一个值得写进简历的诚实发现。
   报两个数即可：**`abstain_rate_on_unanswerable`**（越高越好）与
   **`recall@5_on_answerable @ 同一阈值`**（代价）。
3. **注意**：`hybrid` 根本没有可用的置信信号。`fusion.py:66` 只累加 `weight / (k + rank)`，
   分数量级被完全丢弃——RRF 的 top-1 分数对任何查询都在 `2/61 ≈ 0.0328` 附近。
   所以拒答只能建在**融合前**的某一路上（BM25 分数，或余弦相似度），
   这一点在实现之前就该想清楚，否则会白写一版。

## S5（中高）负样本的"稀有度闸门"实际上从未拒绝过任何东西——两个独立的 bug

**任务书第 5 问的直接回答（抽查结论在最后）。**

**现象 A：大小写 bug。** `keyword_rarity` 用 `tokenize()` 取词，而 `tokenize` 会
**先 lowercase**（`bm25.py:38`）；但 df 是拿小写 token 去**原始大小写**的正文里做子串匹配：

```python
# scripts/build_eval_dataset.py:117
df = sum(1 for text in corpus.values() if token in text)
```

`corpus` 在 `:151` 存的是 `note.read_text()` 原文。实测：小写 `kubernetes` 在语料里 df = **0**，
而 `Kubernetes`（大写 K）实际出现在 **2 篇**里。`eval/dataset.report.md:28` 因此把
`kubernetes` 的文档数记成了 0，**这是错的**。

**现象 B：判据方向反了（这条更致命）。** `keyword_rarity` 返回**最小** df 的 token
（`build_eval_dataset.py:118-120`），`:209` 再判 `if df <= NEGATIVE_MAX_DOC_FREQ`。
也就是说：**只要问题里存在任意一个冷门词，这条负样本就通过**。

中文二字组几乎必然能凑出一个 df = 0 的垃圾片段。看 `eval/dataset.report.md:29-45` 保留下来的"最稀有关键词"：

| --- | --- |
| `注中` | "生命周期标**注中**的协变" |

这些都不是主题词。结果就是 **18 条候选 18 条通过、0 条被丢**

   `df_max_over_content_tokens <= NEGATIVE_MAX_DOC_FREQ`。

## S6（中）表面 6 个指标，实际只有 1 个独立统计量

**现象**：每条可回答问题的 `relevant_notes` 恰好只有 **1 篇**（实测 180/180，每篇笔记恰好 3 条问题）。
在"单个二值相关文档"下，四个指标全部是**同一个量**——"那唯一一篇笔记的命中名次 r"——的函数：

- `recall@k` = `1[r ≤ k]` —— 也就是说它其实是 **Success@k / Hit Rate@k**，不是教科书意义上的 recall
- `precision@k` = `recall@k / k` —— 实测严丝合缝：`0.8283 / 10 = 0.0828` ✓，`0.7879 / 5 = 0.1576` ✓
- `MRR` = `1/r`
- `nDCG@k` = `1/log2(r+1)`（`metrics.py:84` 的 `2^1-1 = 1`，`metrics.py:86-89` 的 `idcg = 1`）
  实测 `ndcg@1 == recall@1 == precision@1 == 0.5758` ✓

**为什么是问题**：`exp-001` 那张 8 行的表看起来像 8 个角度的证据，其实是**一个命中名次分布**
加**一个延迟**。面试官问"为什么 nDCG 和 MRR 结论一致"，正确答案是"因为在单标签下它们必然一致"，
说不出来就很尴尬。

**这不是 bug**：`metrics.py` 支持分级相关（`_as_grades`，`metrics.py:23-26`），
是数据集没用上。

**最小修复**（按性价比排序）：

1. **先改叫法**：把 `recall@k` 在文档里标注为 "recall@k (= Success@k, 单标签)"。
   一行注释，立刻消除歧义。这一条零成本，建议无论如何都做。
2. **在表里删掉 `precision@k`**，它恒等于 `recall@k / k`，不提供任何信息
   （`cli.py:143` 的 `metrics` 列表本来就没有它，只有 `format_report` 打到 stdout 的那份有）。
3. 想让 nDCG 真正发挥作用，就得有分级标签：给"同一篇笔记的中文/英文孪生"打 grade 1、
   原文打 grade 2（见 S8）。这是唯一能让 nDCG 与 MRR 分道扬镳的改法。

## S7（中）语言不均衡确实让 `vector` / `hybrid` 失真，而且样本是按笔记聚簇的

**任务书第 4 问的直接回答。**

**现象**：135 EN + 45 ZH，实测分语言：

| mode | EN (n=135) R@5 | ZH (n=45) R@5 | 差 |
| --- | --- | --- | --- |
| `keyword` | 0.8667 | 0.8667 | **0.000** |
| `vector` | 0.3111 | **0.4889** | +0.178 |
| `hybrid` | 0.6370 | **0.7556** | +0.119 |

**为什么是问题**：`keyword` 完全不受影响，但 `vector` 在中文上高出 **57% 相对**。
原因在 `bm25.py:40-48`：中文被切成**unigram + bigram**，一句中文问题产生的特征数远多于
同长度英文，hashing 嵌入（`embed.py:50-57` 复用同一个 `tokenize`）因此在中文上的信噪比更好。
**结论：调整中英比例会移动 `vector` 和 `hybrid` 的数字，但不会移动 `keyword` 的。**
也就是说，"`keyword` 比 `hybrid` 高多少"这个差值本身是语言配比的函数——
25% 中文这个比例是怎么来的没有记录，它是一个未被声明的自由参数。

**该不该分语言报**：该。但直接分语言会踩另一个坑——

**样本不是独立的，是按笔记聚簇的**：180 条问题来自 **60 篇笔记，每篇恰好 3 条**
（`build_eval_dataset.py` 的候选目录 `eval/candidates/` 有 60 个 json）。
中文那一组只有 **15 篇笔记**。同一篇笔记的 3 条问题，命中与否高度相关
（同一篇笔记要么被检出要么不被检出）。按问题做 bootstrap 会低估方差：

| | 点估计 | 按问题 bootstrap 95% CI | **按笔记聚簇 bootstrap 95% CI** |
| --- | --- | --- | --- |
| `keyword` R@5（可回答 180） | 0.8667 | [0.8167, 0.9111]（宽 0.094） | **[0.8000, 0.9222]（宽 0.122）** |

聚簇 CI 宽 **23%**。中文单独一组（n=45 / 15 篇）按问题算就已经是 **±10 个点**，聚簇后更宽——
在这个精度下，中英之间 0.178 的差在 `vector` 上仍然成立，但任何更细的比较都不可信。

**最小修复**：

1. `cmd_eval` 输出时按 `lang` 切片（`dataset.jsonl` 里加一个 `lang` 字段，编译期用
   `re.search(r'[\u4e00-\u9fff]', question)` 判定即可，`build_eval_dataset.py:193-200` 一行）。
2. 报区间不报点值，且 **bootstrap 的重采样单位必须是 `note_path`，不是问题**。
   20 行代码，不引依赖。
3. 中文组样本量太小的解法**不是**做更宽的置信区间，而是**补数据**：
   把中文目标笔记从 15 篇提到 45 篇（语料里有 972 篇中文笔记，够用），
   让两组的**笔记数**而不是问题数接近。在那之前，中文一列请明确标注 `n=15 notes, 仅供参考`。

## 第 3 问：`answer_span` 逐字校验挡得住什么、挡不住什么

**挡得住**（而且挡得很漂亮，零成本、可复现、比再叫一个模型判断更可靠）：

  `normalize_ws(span) not in corpus_normalized[note_name]`。
- 归错笔记：span 在别的笔记里、不在被标注的那篇里，会被同一条规则拦下。
- 空白差异导致的误杀：`normalize_ws`（`:81-83`）压掉所有空白，这个处理是对的。
- 实测副产品：它顺带保证了**标注笔记的唯一性**（见上文"无问题"一节）。

**挡不住**（按危害排序）：

1. **span 真实存在，但根本回答不了那个问题。** 这是任务书特别点名的情形，

   **没有任何蕴含关系检查**。模型完全可以生成一个真实的句子，配一个它答不了的问题。
   *最小修复*：这是唯一一处**必须**用模型的地方。加一道**二次判定**：
   把 `(question, answer_span)` 交给一个便宜模型，只问一个二元问题

2. **问题照抄了笔记里的稀有标识符**（S1）。span 校验非但挡不住，

3. **span 只是问题的一部分答案。** 现在只要长度在 [10, 400]（`:34-35`）就行，

4. **问题可能同时被另一篇笔记回答**（S8 的孪生，以及 `archived`/`implemented` 同主题笔记）。

## 第 6 问：能不能在简历 / README 里写"hybrid 把 recall@5 从 X 提升到 Y"？

### 不能。而且理由有两层，必须分开说。

### 第一层：**事实上就没有这个提升**

在你自己的数据上，`hybrid` **显著差于** `keyword`：

| （180 条可回答问题） | recall@5 | 按笔记聚簇 bootstrap 95% CI |
| --- | --- | --- |
| `keyword` | **0.8667** | [0.8000, 0.9222] |
| `hybrid` | 0.6667 | [0.5833, 0.7500] |
| `vector`（精确余弦） | 0.3556 | [0.2778, 0.4389] |

配对差（同一批问题，聚簇 bootstrap）：

- `keyword − hybrid` = **+0.2000**，95% CI **[0.1333, 0.2667]** —— 不含 0，**结论稳固**
- `hybrid − vector` = +0.3111，95% CI [0.2389, 0.3889] —— 不含 0

所以"hybrid 提升了 recall"这句话，在当前证据下是**反的**。写它就是撒谎。

### 第二层：**即使方向反过来，当前口径也撑不起这个断言**

`X → Y` 这种因果句式要求"只有融合这一个变量在动"。现在至少有 6 个东西同时在动：

| # | 缺什么 | 归类 | 对数字的影响 |
| --- | --- | --- | --- |
| S1 | 问题照抄笔记里的稀有标识符 | **口径** | df≤2 组 BM25 满分、df>50 组只有 0.676 —— 整张表向词法检索倾斜 |
| S2 | 3 条问题的目标笔记从未被索引 | **口径** | 所有模式白扣 1.67% |
| S3 | `vector` 列被 HNSW 近似额外压低 | **口径** | recall@10 −9.1 点，且归因被写错 |
| S4 | 18 条不可回答问题恒记 0 | **口径** | 所有数字统一 ×0.909，零判别力 |
| S6 | 单标签 → 6 个指标只有 1 个统计量 | **口径** | 证据面比看起来窄得多 |
| S7 | 中英配比 25% 是未声明的自由参数 | **口径** | 只移动 `vector`/`hybrid`，不移动 `keyword` |

### 口径问题 vs 模型能力问题——明确切开

**是口径问题的**（修了数字就会变，上表 S1–S7 全部）：
它们**不改变 `keyword > hybrid` 的方向**（配对差的 CI 不含 0，量级也远大于这些偏差的合计），
但它们会**显著改变幅度**，也会改变你对"为什么"的解释。
尤其 S3：现在写在实验文档里的归因（"31.8% 全是因为 hashing 嵌入没语义"）**部分是错的**。

**是模型能力问题的**（把 S1–S7 全修好也不会变）：

> hashing 嵌入（`embed.py:41-57`）是把 token 哈希进 384 个桶。
> 它**没有语义**，只有有损的词法信号。RRF（`fusion.py`）只消费名次，
> 它把一路强召回和一路弱召回**平均**到一起——这是 RRF 的正确行为，不是 bug。
> **一路无效的召回器，融合只会拉低效果。**

`exp-001:61-66` 这一节写得对，应当保留。这是一个真正的、经得起追问的技术判断。

### 那么现在能诚实地写什么

可以写的（每一句都有数据支撑）：

- > "自建 198 条标注评测集（180 可回答 + 18 不可回答），实现 pgvector 向量检索、
  > 进程内 BM25、RRF 融合三条链路并做四模式消融，**四种模式共用同一实现**。
  > 在离线 hashing 嵌入基线下，BM25 recall@5 = 0.87、hybrid = 0.67 ——
  > **融合一路无效召回器会拉低效果，这是 RRF 的已知行为**；
  > 据此把'接入真实语义嵌入'定为 P0，而不是先去调融合权重。"
- > "评测暴露出 p95 延迟瓶颈在 BM25 的全量扫描（709 ms / 17520 chunk），不在向量检索（54 ms）。"
- > "reranker 当前是 no-op，消融表如实显示 `hybrid_rerank == hybrid`，不制造虚假提升。"

**这比"hybrid 提升了 recall"有说服力得多。**
"我建了评测、评测告诉我我的假设错了、我据此改了优先级"——这正是招聘方想看到的那个信号。
反过来，一个只会向上的指标表，第一个追问就会碎。

### 想真正说出"hybrid 提升 recall@5"，需要按顺序补的四件事

1. **修 S2 + S10 的断言**（各 4 行）。最便宜，且防止以后再出同类静默错误。
2. **先查 S3**：`SET hnsw.ef_search = 200` 重跑 `vector`。
   在归因错误的基础上做决策，后面每一步都会歪。
3. **修 S1 的词法泄漏**，至少要出那张 df 分组表。
   在此之前，`keyword` 的任何数字都不能当作"检索质量"来引用。
4. **然后**才是 P0 的真实嵌入模型。
   换模型**之前**先把 S8 的孪生标注补上，否则你会看到一个假的 `recall@1` 回归，
   并且会花一天去 debug 它。

做完这四件、`hybrid` 真的超过 `keyword` 之后，那句话才能写——
而且到那时你还能顺带说出"**我知道为什么**"，这比数字本身值钱。
